Spool 26.9.0

Turbonator tunes open, edit and build. A .tpl with no .bin beside it is now a document in its own right, and Spool can assemble one into a flashable ROM.

Windows only. There is no macOS build for 26.9.0; Mac users should stay on 26.1.0 until a signed DMG is published.

Open a tune file on its own

A v2 .tpl is not just a table map — it is assembler source for the calibration block, so it carries the values as well. Spool used to read the definitions and throw the values away, taking bytes from the companion .bin. That left most of a Turbonator distribution unopenable: in the reference archive, 34 of 38 tunes have no .bin next to them.

File → Open now accepts .tpl and .mpt. Every table opens with real values, fully editable, with the same grids, graphs, 3D view and compare you get from a .bin. Save writes back to the .tpl, rewriting only the value tokens — your comments, revision history and column alignment come through untouched.

Pick a .tpl that does have a .bin beside it and Spool opens the pair instead, which is strictly better: a real checksum, a .bin to save, and the ECU tools.

A tune is not a ROM, and Spool says so

A Turbonator tune defines 1.4–4.6 KB of a 16/32 KB address space. The firmware is not in the file. So for these documents the header reads Tune file: … · no ROM image, the checksum indicator is hidden rather than shown as “bad” (there is nothing to sum, and “bad” would read as a fault in your tune), and Spool refuses to save one as a .bin.

Build ROM

File → Build ROM (.bin)… assembles the open tune against the firmware source it names in ;mpassmfile and writes a real, checksummed ROM.

It builds what you are looking at, unsaved edits included, so you can try a change without committing to it first. The assembly runs in a temporary workspace that is deleted afterwards — nothing is written into your folder but the .bin you choose, which defaults to sitting beside the tune.

Two things need to be in place: the matching .asm in the same folder as the tune, and an assembler. Spool finds MPTune's MPAssm.exe automatically if MPTune is installed, and otherwise asks you to point at one once and remembers it. If the assembly fails, you get the assembler's own error text, which names the line.

Expect two bytes to differ from an MPTune build of the same tune: the ChecksumFixupValue table and the stored checksum, which come out swapped. That is arithmetic, not a fault — the checksum covers every byte, so moving one moves the other by the same amount in the opposite direction. Nothing in the firmware reads the fixup byte, and both ROMs carry a valid checksum. Spool's is the one whose calibration matches the tune it was built from.

Recovering firmware source from a listing

An assembler .lst is not a disassembly — it contains the complete source text, verbatim, including everything pulled in with .include. One listing per firmware version is therefore a full backup of that firmware's source.

A new developer tool, lstsplit, unpicks one back into its .asm and .tpl. If a firmware source is ever lost, any ROM built with it can produce it again. Verified across every listing in the reference archive; one was checked byte for byte against the original, all 504,426 of them.

Fixes

  • A tune saved as a .spool project reopened as a ROM. Projects record the image, and rehydrating one always produced a ROM-backed document — which handed Save-as-.bin back on an image that was 94.5% filler. Projects now record what they hold. Projects saved by an earlier build load as ROMs, as they should, but a tune saved by one should be re-saved.
  • The Build ROM save dialog defaults beside the tune rather than wherever a file dialog was last used.

None of this has been run on an engine. The bytes and the checksum are verified against the toolchain's own output; “assembles correctly” and “runs correctly” are different claims.
